⚡ O site abre rápido, mas responde devagar

O que o INP ensina ao dev sobre performance percebida, resposta visual e experiência real do usuário.

INP Core Web Vitals Web Performance UX

Performance não é só carregar rápido. É responder bem quando o usuário clica, digita, abre um menu, usa um filtro ou tenta concluir uma ação.

📌 Ideia central: um site pode passar bem no carregamento e ainda entregar uma experiência ruim na interação.

🚀 A cena que todo dev já viu

A página abre rápido.

O conteúdo principal aparece. O layout parece estável. O banner carrega. O menu está visível. A primeira impressão é boa.

Mas aí o usuário tenta usar.

👉 Toca no menu e ele demora. 👉 Clica no botão e nada parece acontecer. 👉 Digita no formulário e a interface engasga. 👉 Aplica um filtro e a listagem fica pesada. 👉 Abre uma área dinâmica e o site parece travado.

Foi aí que eu entendi uma coisa importante:

Nem todo site rápido parece rápido.

E essa diferença muda bastante a forma como a gente olha para performance.

🧠 Performance percebida: o usuário não mede, ele sente

Quando falamos em performance web, é comum pensar primeiro em carregamento.

  • Quanto tempo a página leva para abrir?
  • Quando o conteúdo principal aparece?
  • O servidor está respondendo bem?
  • As imagens estão otimizadas?
  • O cache está funcionando?

Tudo isso importa. Mas performance percebida vai além.

Ela envolve quatro camadas:

  • Carregar rápido: o conteúdo chega logo.
  • Parecer rápido: a página dá sinais de progresso.
  • Responder rápido: cliques, toques e digitação têm retorno visual.
  • Ser agradável de usar: a interface acompanha a intenção do usuário.

O usuário não abre o DevTools para medir milissegundos.

Ele sente atraso.

Ele sente quando o menu não abre. Ele sente quando o botão não dá retorno. Ele sente quando o campo trava. Ele sente quando a interface não acompanha o dedo no celular.

Performance, no fim, é sensação de fluidez.

⚡ Onde entra o INP

INP significa Interaction to Next Paint.

Em linguagem simples, o INP mede quanto tempo a página leva para dar uma resposta visual depois de uma interação do usuário.

Ele observa interações como:

  • clique com mouse;
  • toque em tela sensível ao toque;
  • tecla pressionada no teclado;
  • abertura de menu;
  • acionamento de botão;
  • digitação em campo;
  • uso de filtros;
  • envio de formulário;
  • navegação em componentes dinâmicos.

Segundo o web.dev, o INP avalia a responsividade da página observando a latência das interações durante a vida útil da visita. Um INP baixo indica que a página respondeu rapidamente para todas, ou quase todas, as interações.

📌 Como ler o INP:

  • ✅ Até 200 ms: boa responsividade.
  • ⚠️ Entre 200 ms e 500 ms: precisa melhorar.
  • 🚨 Acima de 500 ms: experiência ruim.

O ponto mais importante é este:

INP não pergunta apenas se a página apareceu. Ele pergunta se a página respondeu.

🧩 LCP, CLS e INP: cada métrica olha uma parte da experiência

As Core Web Vitals ajudam a separar problemas diferentes.

  • LCP - Largest Contentful Paint: mede quando o conteúdo principal aparece.
  • CLS - Cumulative Layout Shift: mede estabilidade visual, ou seja, se os elementos ficam pulando.
  • INP - Interaction to Next Paint: mede a resposta visual depois da interação do usuário.

Uma página pode ter bom LCP e ainda ter INP ruim.

Exemplo simples:

  • A home de um portal institucional abre rápido.
  • O banner aparece.
  • As notícias carregam.
  • O menu está visível.
  • A nota parece boa.

Mas no celular:

  • o menu demora para abrir;
  • o campo de busca trava;
  • o formulário não dá feedback;
  • o filtro da listagem engasga;
  • o clique parece não ter sido reconhecido.

O usuário não vai dizer:

"Interessante, o LCP estava bom."

Ele vai dizer:

"Esse site está travando."

E, para a experiência real, ele está certo.

🧱 Por que um site responde devagar

Um site pode responder devagar por várias razões. Em projetos reais, quase nunca é uma causa única. Normalmente é acúmulo.

Principais causas:

  • JavaScript pesado demais.
  • Eventos de clique fazendo trabalho caro.
  • DOM grande e difícil de recalcular.
  • Componentes renderizando mais do que precisam.
  • Scripts de terceiros competindo pela thread principal.
  • Plugins carregados em páginas onde não são usados.
  • Templates e page builders adicionando camadas extras.
  • Sliders, galerias, menus e widgets mal configurados.
  • Código legado crescendo sem revisão.
  • Falta de teste em celular real.

Em CMSs como Joomla, WordPress, Drupal e portais institucionais, isso aparece muito.

Às vezes o servidor está bom. O cache está ativo. A página abre. O conteúdo aparece.

Mas o front-end está carregando trabalho demais.

Na hora do clique, o navegador precisa processar script, recalcular layout, aplicar estilo, renderizar e só então pintar a próxima resposta.

Quando esse caminho fica pesado, o usuário sente.

🧭 O olhar do dev full stack

Performance não mora em uma única camada.

Quem trabalha com portal, CMS, template, extensão, banco e regra de negócio precisa olhar o caminho inteiro:

  • HTML;
  • CSS;
  • JavaScript;
  • banco de dados;
  • CMS;
  • plugin;
  • template;
  • cache;
  • imagens;
  • scripts externos;
  • experiência mobile;
  • fluxo real do usuário.

O problema pode estar:

  • em uma consulta lenta no banco;
  • em um plugin carregado globalmente;
  • em uma biblioteca JavaScript pesada;
  • em um menu mobile mal implementado;
  • em um componente que recalcula tudo a cada clique;
  • em um formulário que não dá feedback visual;
  • em uma página com DOM grande demais.

O olhar full stack ajuda porque muda a pergunta.

Não é só:

"O site está lento?"

É:

"Qual parte do caminho está atrasando a resposta que o usuário espera?"

🛠️ 5 ferramentas principais para verificar INP e Core Web Vitals

Abaixo estão as ferramentas que eu usaria primeiro em uma auditoria técnica. Cada uma responde uma pergunta diferente. Nenhuma substitui a outra.

1. PageSpeed Insights

🔗 Link: https://pagespeed.web.dev/ 📚 Documentação: About PageSpeed Insights - Google for Developers

O que faz:

  • Analisa uma URL em mobile e desktop.
  • Mostra dados de campo, quando há dados suficientes do Chrome User Experience Report.
  • Mostra dados de laboratório gerados pelo Lighthouse.
  • Aponta oportunidades de melhoria.

O que verifica:

  • LCP;
  • INP;
  • CLS;
  • FCP;
  • TTFB;
  • TBT;
  • peso de recursos;
  • JavaScript e CSS bloqueantes;
  • imagens e oportunidades de carregamento.

O que valida:

  • Se a página passa ou não nas Core Web Vitals.
  • Se o problema aparece em dados reais de usuários.
  • Se mobile e desktop têm comportamentos diferentes.

Cuidado técnico:

  • PageSpeed é ótimo para visão inicial, mas não simula todos os cliques reais do usuário.
  • Se o INP estiver ruim, ele aponta o problema, mas você ainda precisa investigar a interação específica.

2. Chrome DevTools - Performance

🔗 Link: Chrome DevTools Performance features reference

O que faz:

  • Grava uma sessão real de uso da página.
  • Permite clicar, abrir menu, digitar, filtrar e interagir enquanto a gravação acontece.
  • Mostra o que o navegador estava fazendo na thread principal.

O que verifica:

  • long tasks;
  • event handlers lentos;
  • scripts pesados;
  • tempo de renderização;
  • recálculo de estilos;
  • layout;
  • paint;
  • interações acima de 200 ms;
  • atraso entre input, processamento e apresentação visual.

O que valida:

  • Se o gargalo está antes do handler, durante o JavaScript ou na renderização.
  • Se o clique demora por causa de script, layout, pintura ou trabalho concorrente.
  • Qual função, arquivo ou componente está consumindo tempo.

Cuidado técnico:

  • Grave fluxos reais, não só o carregamento.
  • Use CPU throttling para simular aparelhos menos potentes.
  • Teste menu, formulário, busca, filtro e componentes dinâmicos.

3. Lighthouse

🔗 Link: Lighthouse - Chrome for Developers

O que faz:

  • Executa auditorias automatizadas em ambiente controlado.
  • Pode ser usado no Chrome DevTools, PageSpeed Insights, linha de comando ou Node.
  • Avalia performance, acessibilidade, boas práticas e SEO.

O que verifica:

  • performance score;
  • métricas de carregamento;
  • Total Blocking Time;
  • recursos bloqueantes;
  • JavaScript não utilizado;
  • imagens não otimizadas;
  • acessibilidade;
  • boas práticas;
  • SEO técnico básico.

O que valida:

  • Se existe regressão técnica entre uma versão e outra.
  • Se há oportunidades claras de otimização.
  • Se o site tem problemas de performance em laboratório.

Cuidado técnico:

  • Lighthouse ajuda muito, mas a nota não conta a história inteira.
  • Uma pontuação boa não garante que todas as interações reais estejam rápidas.

4. Google Search Console - Core Web Vitals

🔗 Link: Relatório de Core Web Vitals - Search Console

O que faz:

  • Mostra dados reais de usuários para páginas indexadas.
  • Agrupa URLs por status: bom, precisa melhorar ou ruim.
  • Separa dados por dispositivo, como mobile e desktop.

O que verifica:

  • grupos de URLs afetadas;
  • LCP;
  • INP;
  • CLS;
  • status por tipo de dispositivo;
  • evolução do problema ao longo do tempo.

O que valida:

  • Se o problema é isolado ou afeta várias páginas.
  • Se uma correção melhorou um grupo de URLs.
  • Se o problema aparece em uso real, não só no laboratório.

Cuidado técnico:

  • Ele não mostra a função JavaScript culpada.
  • Ele mostra onde há problema em escala. Para descobrir a causa, combine com DevTools, PageSpeed e testes reais.

5. WebPageTest

🔗 Link: https://www.webpagetest.org/ 📚 Documentação: WebPageTest Documentation

O que faz:

  • Testa páginas em locais, conexões e dispositivos configuráveis.
  • Mostra waterfall, filmstrip, tempo de carregamento e comportamento visual.
  • Ajuda a comparar cenários de rede e performance.

O que verifica:

  • carregamento inicial;
  • waterfall de recursos;
  • bloqueios de rede;
  • peso da página;
  • tempo de renderização;
  • Core Web Vitals observadas no teste;
  • comportamento visual ao longo do carregamento.

O que valida:

  • Se o problema muda conforme localidade, rede ou dispositivo.
  • Se scripts de terceiros atrasam o carregamento.
  • Se recursos críticos estão bloqueando a experiência.

Cuidado técnico:

  • WebPageTest é excelente para laboratório e comparação controlada.
  • Para INP, continue testando interações reais no DevTools e, quando possível, com dados de campo.

🔗 Outras ferramentas úteis

Essas entram como apoio, monitoramento ou investigação mais avançada:

  • CrUX Vis - visualiza histórico de dados reais do Chrome UX Report.
  • Documentação do CrUX Vis - explica dados históricos, URL/origin e dispositivos.
  • web-vitals JavaScript library - mede Web Vitals em usuários reais dentro da aplicação.
  • PageSpeed Insights API - permite automatizar consultas de performance.
  • Lighthouse CI - ajuda a monitorar regressões em pipelines.
  • DebugBear INP Debugger - testa interações e ajuda a encontrar elementos com atraso.
  • DebugBear Web Vitals Report - combina dados de laboratório, CrUX e monitoramento.
  • HTTP Archive - CrUX - relatórios públicos com dados agregados de experiência real.

🧪 Roteiro prático de investigação

Eu seguiria este fluxo:

  1. Comece pelo PageSpeed Insights.
  • Veja se há dados de campo.
  • Compare mobile e desktop.
  • Observe LCP, CLS e INP separadamente.
  1. Abra o Search Console.
  • Veja se o problema aparece em grupos de URLs.
  • Priorize páginas com maior impacto.
  • Separe problemas mobile de desktop.
  1. Reproduza o problema no navegador.
  • Use um celular real.
  • Teste rede comum.
  • Clique em menus.
  • Digite em formulários.
  • Use filtros, buscas, modais e sliders.
  1. Grave no Chrome DevTools Performance.
  • Interaja durante a gravação.
  • Procure long tasks.
  • Observe a trilha de interações.
  • Veja se o atraso está no input delay, processing duration ou presentation delay.
  1. Use Lighthouse e WebPageTest para hipóteses controladas.
  • Compare antes e depois.
  • Meça impacto de scripts, imagens e terceiros.
  • Documente cada alteração.

⚠️ Erros comuns

Alguns erros aparecem com frequência em auditorias:

  • Achar que nota alta resolve tudo.
  • Testar só no desktop potente.
  • Medir apenas carregamento inicial.
  • Ignorar cliques, menus e formulários.
  • Instalar plugin para resolver problema de arquitetura.
  • Carregar script global para recurso usado em uma única página.
  • Otimizar imagem e esquecer JavaScript.
  • Ignorar mobile.
  • Confundir cache com experiência.
  • Celebrar LCP bom enquanto o INP está ruim.

Nota ajuda. Relatório ajuda. Gráfico ajuda.

Mas se o usuário clica e a interface não responde, a experiência continua ruim.

✅ Boas práticas para melhorar resposta e INP

Algumas decisões costumam ajudar bastante:

  • Reduzir JavaScript desnecessário.
  • Carregar scripts apenas onde são usados.
  • Dividir tarefas longas em partes menores.
  • Evitar handlers de clique pesados.
  • Dar feedback visual rápido.
  • Simplificar DOM.
  • Revisar componentes que renderizam demais.
  • Remover plugins duplicados ou sem uso.
  • Evitar sliders e builders pesados sem necessidade.
  • Reduzir scripts de terceiros.
  • Usar cache com critério.
  • Testar fluxos reais.
  • Medir em mobile.
  • Monitorar depois da publicação.

Em portais institucionais, uma revisão simples já pode revelar muita coisa:

  • Quais plugins carregam em todas as páginas?
  • Quais scripts são realmente usados?
  • O template injeta CSS e JS demais?
  • O menu mobile depende de biblioteca pesada?
  • A busca faz trabalho demais a cada tecla?
  • O formulário dá feedback imediato?
  • O usuário sabe que a ação foi recebida?

Pequenas decisões técnicas viram sensação de velocidade.

🧾 Conclusão

Performance não é vaidade técnica.

É respeito pelo tempo do usuário.

Um site bom não é apenas o que aparece rápido. É o que responde quando alguém precisa dele.

O INP lembra o dev de uma coisa simples e importante:

  • a experiência não termina no carregamento;
  • ela continua em cada clique;
  • continua em cada toque;
  • continua em cada campo preenchido;
  • continua em cada menu aberto;
  • continua em cada ação concluída.

No fim, performance real é quando a interface acompanha a intenção.
